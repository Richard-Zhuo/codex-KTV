# 金碧辉煌 KTV 管理系统

面向 KTV 门店实际经营管理的系统，覆盖员工操作、房间与订单、酒水库存、收款、权限审批、设备协同、经营查询和数据恢复。

**核心目标：老板连续 14 天不在门店，经过授权的员工仍能安全、正确、持续营业；老板可以在店外监督经营、审批必要事项、接收异常告警并处理故障。**

项目优先级：业务正确性 > 资金、库存、权限和数据安全 > 员工可用性 > 架构优雅。

## 当前状态

**目前不能作为已验收的正式生产营业系统直接投入使用。** 已实现、隔离环境验收和生产验收是不同状态。

- **正常营业增量验收已接受并关闭**：2026-10-31，Owner 在真实 Edge 员工页面完成同一笔新合成订单的收余款、结账和清洁；可信 MySQL 核对确认付款唯一、金额一致、房态正确，且没有重复扣库存，测试资源已清理。
- **正式服务端数据路径已有实现及相应验收证据**：员工端和管理后台通过 HTTP API 使用服务端认证、具体权限校验及 MySQL 可信账本，不再仅是浏览器本地演示。
- **生产门禁尚未闭合**：R2 整体验收仍为 `BLOCKED`，G1-A L1 路线保持 `PAUSED_NO_GO`；正式异地备份、独立密钥保管、异机恢复及生产 RPO/RTO 尚未验收。云端主生产部署、店外安全访问、真实告警和真人员工离岗演练仍有未完成项。

## 技术架构

- **前端**：原生 HTML、CSS 和 JavaScript ES Modules。员工端由 `ui/staff-app.js`、管理后台由 `ui/admin-app.js` 进入正式 API 数据路径。
- **服务端**：Node.js HTTP API（`http/`），组合认证（`auth/`）、业务规则及可信事务账本（`ledger/`）。写操作使用 `operationKey` 和 `expectedRevision` 进行幂等与并发校验；服务端重验会话和当前权限，并保留 Origin/CSRF 保护。
- **可信存储**：MySQL 8.4 / InnoDB，当前采用版本化业务快照，业务状态、操作结果和成功审计在同一事务中提交。[`database/migrations/`](./database/migrations/) 中的版本化迁移是唯一正式 schema authority；旧 PostgreSQL `schema.sql`、`seed.sql` 仅保留为历史参考。
- **设备与运行保障**：`devices/` 持久化设备工作流，外部设备调用在 SQL 事务之外执行；`backup/`、`recovery/` 和 `operations/` 分别承担备份、恢复控制与监测告警。现有通用恢复入口限制为独立 TEST 数据库，普通生产恢复执行入口仍禁用。

仓库仍保留早期浏览器 `localStorage` 演示实现及相关历史材料。它们与正式服务端数据路径应分别理解：浏览器本地状态、演示角色或普通页面响应不能单独作为真实认证、资金账本或生产验收证据。详细边界见[系统架构](./docs/ARCHITECTURE.md)和[数据库说明](./database/README.md)。

## 开发路线与生产限制

下一步围绕 14 天离岗所需的实际能力收敛，主要剩余门禁包括：

- 正式异地备份、独立密钥取回及异机恢复，验证 **RPO ≤ 1 小时、RTO ≤ 4 小时**；组件测试或同机隔离恢复不能替代生产灾难恢复验收。
- **云端主生产系统**部署、私网/TLS 与店外安全访问；门店电脑不作为唯一生产主机。
- 老板远程经营查询、审批及异常处理，告警实际送达、主机失联监测和故障响应。
- 真人员工在既定权限内独立营业、跨班交接及应急操作，资金异常处置和必要经营报表。

上述事项尚未全部闭合，不能因单笔业务补验通过就宣布离岗 MVP 就绪。生产恢复、真实云资源及外部服务操作必须单独取得授权；R2/G1-A 的冻结、暂停和验收边界保持有效。详细进度与阶段历史统一见[当前阶段](./docs/CURRENT_STAGE.md)。
