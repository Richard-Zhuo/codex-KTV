## Independent pre-smoke audit fix (2026-10-11)

The review independently reproduced two P1 risks. First, after a notified recipient was removed from current routing, the persisted RESOLVED delivery selected that recipient but the WeCom transport rejected it with WECOM_RECIPIENT_INVALID before any network request; a previously reserved OPEN retry could fail the same way after a config change. Second, an unknown persisted severity would fall through to WARN recipients instead of failing closed.

The narrow fix authorizes a historical delivery only when its persisted outbox identity and recipients match the same incident. RESOLVED additionally requires that incident's persisted accepted or possibly notified recipient union. New deliveries still use the current CRITICAL/ERROR or WARN policy. Unknown severity, IDs, empty recipients and broad targets fail closed before network activity. The separate recoveryRecipients setting was removed before production release because the protected incident/outbox snapshot is the stable authority. A departed or invalid WeCom account can still cause provider rejection; the delivery remains visible and readiness degrades.

Post-fix synthetic evidence: focused WeCom/operations/production suite 30/30 PASS, 0 fail, 0 skip; Stage 5E isolated crash-recovery rehearsal 1/1 PASS with fixture cleanup. Two full 2201/2201 PASS runs preceded the second P1 fix. After that fix, the latest comparable full regression was 2200/2201, one Stage 5E 503 in creditAndCash, exit 1. These failures occur in the Fake transport rehearsal and the modified WeCom code is not used there; causality remains unproven. ## Stage 5E 503 root-cause reconciliation (2026-10-11)

Verdict: **EXISTING BUG EXPOSED BY TIMING**. This is an existing Stage 5D alert-readiness defect, with a Stage 5E harness recovery-read race. It is not caused by the S2 WeCom recipient or severity fixes. Stage 5E imports the pinned accepted Stage 5D runtime package c1502c0fb0713ef040b210e5ea35f6c31079b7ee and uses FakeAlertTransport; no WeCom token, provider client, protected WeCom recipient list or external network is involved.

The two unexplained historical failures were GET /api/v1/store/snapshot during creditAndCash and GET /api/v1/admin/snapshot after database unlock and a successful /health/ready check. Each returned 503 with the safe API code service_unavailable; those old TAP records did not capture the exact readiness blocker at the instant of failure, so that fact is not claimed. The independently captured database-outage 503 was expected: POST /api/v1/commands/clean returned service_unavailable, /health/live stayed 200, /health/ready was 503 with DATABASE_OR_SCHEMA_UNAVAILABLE, operational database was unavailable, recovery mode NORMAL, worker ENABLED, and the runtime PID was recorded in external TAP. After DB restoration, readiness can temporarily change again while Fake alert delivery is in flight. A prior successful ready read cannot guarantee a later business read will remain ready.

The alert dispatcher persists attempts=1 and PENDING before awaiting its first send. The old readiness predicate treated every such row as ALERT_DELIVERY_UNAVAILABLE, including an ordinary first send that had not failed. A deterministic held-send probe against accepted main 6b713f52accda8b3292959ed4fea8b2690c2b78f and the pre-fix S2 candidate both showed PENDING/attempts=1, ALERT_DELIVERY_UNAVAILABLE during send, then no blocker after accepted delivery. The candidate after the narrow production fix reported no blocker during that first send and no blocker after success. The same held recovery alert in the pinned Stage 5D rehearsal package forced /health/ready to 503 with ALERT_DELIVERY_UNAVAILABLE, proving the timing mechanism; the old harness failed at the next DB-recovery business read under that forced timing. An isolated accepted-main Stage 5E run and the candidate's pre-fix isolated 5/5 both passed without the forced hold; ordinary runs alone do not disprove the race.

The production fix tracks only process-local first in-flight sends and excludes that state from the alert-delivery readiness blocker. An actual rejected, timed-out, exhausted, persisted-after-restart or retrying delivery remains degraded. The rehearsal fix waits for the exact held recovery delivery to be accepted and for /health/ready and the safe business GET to succeed; GET-only 503 retries are bounded. It does not retry a business command or add a fixed delay. Stage 5E retains the pinned accepted package, so the rehearsal verifies its existing 503 behavior before crossing the recovery checkpoint. Incident/outbox identities, recipient snapshots, severity validation, RESOLVED/INFO routing and the two earlier S2 P1 fixes are unchanged.
