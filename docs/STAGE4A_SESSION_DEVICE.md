## Device workflow boundary (Commit 2)

No HTTP endpoint or formal employee open invokes devices/application.js in Stage 4A. Its internal start accepts only operationKey, expectedRevision and an existing orderId. Existing session revalidation and room.open permission run in each claim transaction; the principal is server resolved and saved as workflow actor. Start derives room/session/target only from the locked ledger order. Mapping is an explicit immutable server configuration of internalRoomId, provider, externalDeviceId, enabled; duplicate target devices are rejected. Only synthetic mappings exist in tests.

Migration 008 adds room_control_workflows (InnoDB), scoped by ledger, with unique order and operation keys, immutable actor/fingerprint identity, monotonic version and checksummed JSON. Business order/payment/inventory/revision remain untouched; readiness is a separate workflow projection. Replaying start returns the existing workflow; a second key for the same order conflicts. Foreign actor replay conflicts and foreign actor resume is denied. Formal order/device integration and transactional outbox creation during open remain Stage 4C, after safe Stage 4B mutation validation.

State path: DEVICE_PENDING -> DEVICE_CLOSING -> DEVICE_OPENING -> DEVICE_VERIFYING -> ACTIVE. roomReadiness is OPENING until actual final verification, WAITING_DEVICE while offline, ACTIVE only after online/open/correct target evidence, FAILED on known terminal failure. DEVICE_OFFLINE_WAIT retains its original workflow and step, then resumes after online. DEVICE_UNKNOWN means effect not proven; queryRoomState is required first. Definitive failure requires settled evidence. Raw provider responses, diagnostics, cookies and credentials are not persisted; only scoped boolean/status evidence is retained.

Each advance executes one step: transaction A locks head/workflow, reloads auth, records attempt/lease and commits; external ensureSession/status/action runs after all DB locks release; transaction B fences the attempt ID, saves sanitized evidence and advances. Active in-flight duplicates send nothing. After a crash or ambiguous commit, a surviving claim is reconciled after lease expiry; late responses cannot overwrite a newer claim. Unknown mutations require scoped step identity and definitive settled APPLIED evidence, or definitive settled NOT_APPLIED plus explicit retrySafe before retry. Plain current on/off status is insufficient to prove an uncertain mutation. Providers lacking this proof stay UNKNOWN for reconciliation. Session expiry or changed order/mapping stops fresh mutations; uncertain old mutations can still be queried. No DB transaction waits for a device to come online.

Gateway methods: ensureSession, getRoomStatus, closeRoom, openRoom, queryRoomState. openRoom accepts externalDeviceId, countdownSeconds and targetEndAt as one combined provider effect: open and establish the target together. There is no independent setCountdown capability or TIMER step. countdownSeconds is the existing trusted ceil-to-minute duration multiplied by 60; provider unit, rounding, limits and zero behavior still require safe verification in Stage 4B. FakeKtvRoomControlGateway requires explicit isolated test mode and simulates online/offline/applied/unknown/timeout/recovery. KtvSkyRoomControlGateway is intentionally disabled. The boundary expresses combined domain intent; it does not claim verified real mutation semantics. The observed KTVSky frontend can map CLOSE to status=0 and OPEN to status=1 plus opentime=countdownSeconds in one request. Stage 4B must default to close -> open-with-countdown -> verify and must not implement openRoom() -> setCountdown() without new safe capability evidence. See [actual discovery](KTVSKY_CAPABILITY_DISCOVERY.md).

Cases and evidence: ONLINE close/open-with-countdown/verify -> ACTIVE; OFFLINE -> WAIT -> same workflow; lost response -> UNKNOWN -> scoped query -> recover without duplicate mutation; concurrent calls -> one claim; SQL/commit uncertainty -> query original identity; auth loss -> no dispatch. Real MySQL integration verifies persistence across connections and proves a second connection can lock the head and workflow during every gateway call. Automated tests use only synthetic devices and the guarded disposable MySQL fixture. No real device mutation, mapping or credential is required.
