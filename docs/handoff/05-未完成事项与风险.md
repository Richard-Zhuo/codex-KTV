# 未完成事项与风险

以下内容必须与“已经完成的演示功能”区分。它们不是小缺陷，而是从单机演示走向真实营业系统时需要单独设计和验收的工作。

## P0：正式使用前必须完成

### 服务端与数据库接入

- 当前 `server.js` 只提供静态文件，没有业务 API。
- PostgreSQL 结构已经存在，但页面没有连接数据库，也没有迁移执行器。
- 必须把权限、房态、订单、库存、挂账、审核和幂等校验移到服务端事务中。
- 需要正式的数据库迁移、连接池、环境配置、健康检查、日志和错误处理。

### 真实认证与授权

- 当前身份可在界面中自由切换，只适合演示。
- `/admin` 的权限检查发生在浏览器端，不能作为安全边界。
- 需要账号登录、会话管理、密码或企业身份接入、服务端权限校验、离职禁用和操作审计。

### 多设备一致性

- 当前数据只在一个浏览器来源的 `localStorage` 中。
- 没有多手机同步、并发版本、冲突解决、服务器账本或实时刷新。
- 正式版必须保证房态、库存、挂账余额和支付不被并发覆盖。

### 支付、平台券和财务

- 微信、支付宝、现金、美团、抖音都只是手工登记。
- 美团／抖音扫码验券只有数据接口占位，尚未对接平台。
- 没有退款、冲正、支付回调、对账、真实日结和资金安全控制。

### 通知、附件和备份

- 预订、客诉和逾期提醒只显示在页面，没有系统通知、短信或钉钉推送。
- 图片凭证保存在浏览器状态，不是可靠附件存储。
- 没有自动备份、恢复演练、归档、对象存储和保留策略。

## P1：明确尚未实现的业务

- 退款、撤单和冲正。
- 并房、换房和多人拆账。
- 会员、营销、优惠券和会员价。
- 存酒转赠、过期、损耗审批和跨店存取。
- 商品、套餐和价格的后台维护。
- 香烟等未明确价格商品的完整库存和销售流程。
- 正式班次切换、班次归属和跨日营业日关账。
- 钉钉发布、企业通讯录、待办和外部通知接入。

## P1：历史数据导入

- 已建立金山营业日报和支出表的原始暂存、映射与 CSV 模板。
- 尚未把用户的实际营业报表导入数据库。
- 导入前需取得原始文件、计算校验和、逐字段验证、保留原文和错误记录，再在单个事务内写入正式表。
- 历史数据缺失支付方式时必须记为“历史汇总未分类”，不能猜测。

## P2：质量与运维

- 尚无持续集成、自动部署、服务守护、监控和告警。
- 尚无真实 PostgreSQL 集成测试、API 测试、端到端并发测试和安全测试。
- 真机触控、系统大字体、输入法遮挡、弱网、断网恢复和多浏览器仍需现场验收。
- 当前浏览器测试不能替代店内网络、收银硬件和实际员工可用性测试。
- 缺少正式隐私政策、数据最小化、敏感信息脱敏和审计查询界面。

## 设计风险

- `app.js` 同时承担渲染、事件和状态迁移，继续增长会降低可维护性；正式版应拆分页面、领域服务和 API 客户端。
- `rules.js` 是单文件领域规则，当前适合演示测试；正式版应按订单、库存、审批、预订等领域拆分，同时保持共享事务约束。
- 本机状态迁移只服务演示，不能替代数据库 schema migration。
- 前端隐藏按钮并不安全；业务规则和数据库约束必须保持双层校验。

## 后续建议顺序

1. 冻结当前演示规则和测试，确认正式版首期范围。
2. 建立后端项目、认证、PostgreSQL migration 和审计框架。
3. 先迁移房间、订单、付款、权限与幂等，再迁移库存、挂账和审核。
4. 建立历史数据导入工具并用副本演练。
5. 接入附件存储、通知和平台验券。
6. 做多设备并发、断网、备份恢复和真机验收。
